# Учёт остатков этикетки — план разработки

Версия плана: 2026-11-06.

## 1. Что делаем

Небольшое веб-приложение для локальной сети: сервер и браузерный интерфейс.

- Таблица актуальных остатков с поиском, сортировкой и фильтром по контрагенту.
- Добавление, редактирование и удаление позиций. Удаление мягкое, с возможностью восстановить.
- Сканирование штрихкода: если позиция есть, открывается её карточка; если нет, открывается форма создания с уже заполненным штрихкодом.
- Журнал изменений остатка. Нужен, чтобы разбирать ситуации «куда делись 500 штук» и для интеграции с 1С.
- Задел под интеграцию с 1С:Предприятие.

Входа и пользователей нет. Сервер работает на локальном сервере в офисе.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Поле `name` | Это контрагент, а не наименование макета. Контрагенты ведутся справочником |
| Номер макета | Только цифры, бывают ведущие нули, всегда уникален |
| Штрихкод | Необязателен, один на позицию, уникален. Партий нет |
| Остаток | Целое число в штуках, не меньше нуля |
| Пользователи | Нет: ни входа, ни ролей |
| БД | PostgreSQL 17 |
| Размещение | Локальный сервер, Docker Compose |
| Учётная система | 1С:Предприятие 8.3 |

## 5. Модель данных

### `counterparties` — справочник контрагентов

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | uuid PK | |
| `name` | text NOT NULL | Название контрагента |
| `external_id` | text NULL, уникальный | ID контрагента в 1С |
| `created_at`, `updated_at` | timestamptz | |

Уникальный индекс `lower(trim(name))`, чтобы не появлялись «Ромашка» и «ромашка » как два разных контрагента.

### `labels` — позиции

| Поле | Тип | Обяз. | Комментарий |
|---|---|---|---|
| `id` | uuid PK | да | Стабильный ID, нужен для 1С |
| `counterparty_id` | uuid FK → `counterparties` | да | |
| `layout_number` | text, `CHECK (layout_number ~ '^[0-9]+$')` | нет | Строка, чтобы сохранить ведущие нули (`00123`) |
| `barcode` | text | нет | |
| `printed_at` | date | да | Только дата, без времени, чтобы день не «съезжал» из-за часовых поясов |
| `quantity` | integer, `CHECK (quantity >= 0)` | да | Остаток в штуках |
| `comment` | text | нет | |
| `version` | integer DEFAULT 1 | да | Оптимистичная блокировка |
| `external_id` | text, уникальный | нет | ID в 1С |
| `created_at`, `updated_at` | timestamptz | да | `updated_at` нужен для инкрементальной выгрузки в 1С |
| `deleted_at` | timestamptz | нет | Мягкое удаление |

Индексы:

- `UNIQUE (layout_number) WHERE deleted_at IS NULL AND layout_number IS NOT NULL`;
- `UNIQUE (barcode) WHERE deleted_at IS NULL AND barcode IS NOT NULL`;
- `counterparty_id`, `updated_at`.

`00123` и `123` — разные номера макета, как и в реальности. Поиск идёт по точной строке и по префиксу. Сортировка по номеру: `length(layout_number), layout_number`, чтобы `9` шёл раньше `10`.

Номер макета и штрихкод необязательны, но позицию всегда можно опознать по контрагенту. Без номера и без штрихкода позиция допустима, в таблице показывается «—».

### `stock_movements` — журнал изменений остатка

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | uuid PK | |
| `label_id` | uuid FK → `labels` | |
| `delta` | integer, `CHECK (delta <> 0)` | +приход / −расход |
| `quantity_after` | integer | Остаток после операции |
| `reason` | enum | `created`, `print` (допечатка), `consumption` (расход), `inventory` (инвентаризация), `correction` (исправление) |
| `comment` | text | |
| `created_at` | timestamptz | |

Кто сделал изменение, не хранится: пользователей нет.

## 6. Правила бизнес-логики

1. **Остаток меняется только через операцию с дельтой.** Одна транзакция:
   `UPDATE labels SET quantity = quantity + $1, updated_at = now() WHERE id = $2 AND deleted_at IS NULL AND quantity + $1 >= 0 RETURNING quantity` и запись в `stock_movements`. Так два одновременных списания не затрут друг друга. Если `UPDATE` не затронул ни одной строки, сервер отвечает 422 «Остаток не может уйти в минус».
2. **Инвентаризация** (задать точное значение) на сервере пересчитывается в дельту внутри той же транзакции, с блокировкой строки `SELECT ... FOR UPDATE`.
3. **Допечатка:** операция `print` увеличивает остаток и, если передана, обновляет `printed_at`.
4. **Остальные поля** редактируются с проверкой `version`. При конфликте 409 «Позицию изменили, обновите данные».
5. **Уникальность.** При дубле номера макета или штрихкода сервер отвечает 409 и указывает, какой позицией занято значение, чтобы фронт показал ссылку на неё.
6. **Восстановление удалённой позиции** невозможно, если её номер макета или штрихкод уже заняты другой активной позицией. Ответ 409 с пояснением.
7. **Нормализация штрихкода** в одном месте, `packages/shared`: убираются пробелы и управляющие символы, кириллица ЙЦУКЕН переводится в латинскую раскладку. При русской раскладке сканер вместо `ABC123` вводит `ФИС123`. С цифровыми EAN этой проблемы нет, с Code128 и буквами есть.
8. **Контрольная сумма EAN-13** не обязательна. Если код похож на EAN, но сумма не сходится, показывается предупреждение, а не ошибка.
9. **Номер макета** проверяется на «только цифры» в zod и `CHECK` в БД. Пробелы по краям обрезаются, ведущие нули сохраняются.

## 7. API

JSON. OpenAPI генерируется из zod-схем, Swagger UI доступен по `/api/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/labels?search=&counterpartyId=&onlyEmpty=&deleted=&sort=&order=&page=&pageSize=` | Список, по умолчанию 50 строк на страницу. Поиск по контрагенту, номеру макета и штрихкоду |
| GET | `/api/labels/by-barcode/:code` | Поиск по скану: 200 или 404 |
| GET | `/api/labels/:id` | Карточка |
| POST | `/api/labels` | Создание. Начальный остаток пишется в журнал как `created` |
| PATCH | `/api/labels/:id` | Редактирование полей, кроме остатка, с передачей `version` |
| DELETE | `/api/labels/:id` | Мягкое удаление |
| POST | `/api/labels/:id/restore` | Восстановление |
| POST | `/api/labels/:id/movements` | `{ delta \| setQuantity, reason, printedAt?, comment? }` |
| GET | `/api/labels/:id/movements` | История позиции |
| GET | `/api/counterparties?search=` | Автодополнение, до 20 вариантов |
| POST | `/api/counterparties` | Создание. Если контрагент уже есть, возвращается существующий |
| PATCH | `/api/counterparties/:id` | Переименование |
| GET | `/api/export.csv` | Выгрузка остатков: UTF-8 с BOM, разделитель `;`, чтобы Excel открывал без настройки |
| GET | `/api/health` | Проверка приложения и соединения с БД |

Ошибки в одном формате: `{ code, message, details? }`.

| Код | Когда |
|---|---|
| 400 | Ошибка валидации, в `details` поля с текстом ошибки |
| 404 | Позиция или контрагент не найдены |
| 409 | Конфликт версии, дубль номера макета или штрихкода |
| 422 | Остаток уходит в минус |
| 500 | Внутренняя ошибка, без стектрейса в ответе |

## 8. Интерфейс

Главный принцип: один экран, одна строка поиска, любое действие за два клика.

```
┌──────────────────────────────────────────────────────────────┐
│ Остатки этикетки                              Удалённые      │
├──────────────────────────────────────────────────────────────┤
│ [ Найти или отсканировать штрихкод…                  ]       │
│ Контрагент: [Все ▾]   [ ] Только нулевые   [+ Добавить]      │
├──────────────────────────────────────────────────────────────┤
│ Контрагент ▲ │ № макета │ Штрихкод      │ Печать     │ Остаток│
│ Ромашка      │ 00123    │ 4600000000017 │ 01.11.2026 │  1 200 │
│ Василёк      │ 0457     │ —             │ 15.10.2026 │ 0 — нет│
└──────────────────────────────────────────────────────────────┘
```

### Экраны и сценарии

- **Главный экран.** Таблица `<table>` с `<caption>`. Сортировка кликом по заголовку: `<button>` внутри `<th>` с `aria-sort`. Пагинация по 50 строк, виртуализация не нужна. В строке кнопки «Изменить остаток» и «Редактировать».
- **Скан, позиция найдена.** Открывается карточка (`<dialog>`) с крупно выведенным остатком, полем количества и кнопками «Списать», «Допечатка», «Инвентаризация». Enter подтверждает списание, Esc закрывает. После операции фокус возвращается в строку поиска, можно сканировать следующую этикетку.
- **Скан, позиция не найдена.** Сообщение «Штрихкод 4600000000017 не найден» и кнопка «Создать позицию»: форма открывается с заполненным штрихкодом.
- **Форма позиции.** Поля: «Контрагент» (автодополнение со справочником, можно ввести новое название), «Номер макета» (`inputmode="numeric"`, ошибка «Только цифры»), «Штрихкод», «Дата печати» (по умолчанию сегодня), «Остаток» (только при создании, дальше через операции), «Комментарий».
- **Удаление.** Диалог подтверждения с контрагентом и номером макета. После удаления появляется уведомление с кнопкой «Отменить».
- **Удалённые.** Отдельный список с кнопкой «Восстановить».
- **История.** Вкладка в карточке: дата, операция, изменение, остаток после, комментарий.
- **Пустые состояния и ошибки.** «Пока нет ни одной позиции — добавьте первую» вместо пустой таблицы. Ошибки сети выводятся в `role="alert"`, при отсутствии соединения показывается «Нет связи с сервером, повторяем…».

### Сканер

Обычный USB или Bluetooth-сканер работает как клавиатура: быстро вводит символы и нажимает Enter.

Хук `useBarcodeScanner` в `features/scanner`:

- слушает `keydown` на `document`; если символы приходят не реже чем раз в ~35 мс, их не меньше 6 и в конце Enter, это скан, даже когда фокус не в строке поиска;
- если фокус стоит в поле формы, глобальный перехват отключается, чтобы скан не ушёл в чужое поле;
- берёт `event.code` (физическая клавиша), а не `event.key`, чтобы не зависеть от раскладки, и дополнительно прогоняет код через нормализацию;
- снимает слушатель при размонтировании и сбрасывает таймер;
- порог и минимальная длина задаются в конфиге.

Сканер должен быть настроен на суффикс Enter. У большинства моделей это стоит по умолчанию, в инструкцию добавляется штрихкод настройки из паспорта сканера.

Сканирование камерой телефона (`BarcodeDetector` / `@zxing/browser`) — отдельный этап, если понадобится.

### Доступность

Это не отдельный этап, а часть каждой задачи:

- семантика: `header`, `nav`, `main`, `section` с `aria-labelledby`, один `h1`, заголовки по уровням;
- модалки на нативном `<dialog>` через `showModal()`: фокус заперт внутри и возвращается на кнопку, которая открыла окно;
- контраст текста не ниже 4.5:1 (крупного — 3:1), границ полей и кнопок — не ниже 3:1, фокус всегда виден;
- размеры в `rem`, масштабирование не блокируется, `prefers-reduced-motion` учитывается;
- нулевой остаток подписан текстом «нет в наличии», а не только цветом;
- результат скана и операций озвучивается через `aria-live="polite"`;
- всё доступно с клавиатуры в порядке чтения.

## 9. Безопасность и надёжность

Входа нет, поэтому любой, кто откроет адрес в локальной сети, может менять и удалять позиции. Что это компенсирует:

- приложение доступно только из локальной сети, порт PostgreSQL не пробрасывается наружу, БД видна только контейнеру приложения;
- удаление мягкое, с отменой и восстановлением;
- все изменения остатка записываются в журнал.

Если позже понадобится защита, проще всего поставить один общий пароль на reverse proxy (Caddy `basicauth`), не трогая код.

Остальное:

- валидация zod на каждом маршруте, запросы только параметризованные через Drizzle;
- rate-limit (`@fastify/rate-limit`) как защита от зациклившегося скрипта или сканера;
- `@fastify/helmet` с CSP для статики;
- в логах не должно быть строки подключения к БД и токенов 1С (redact в pino);
- ограниченный пул соединений (`max: 10`) с таймаутом запроса; при остановке приложение закрывает пул и сервер (graceful shutdown);
- при старте приложение повторяет подключение к БД с паузой и понятным сообщением в логе, а не падает молча, если PostgreSQL ещё поднимается.

## 10. Тесты

**Юнит (`packages/shared`):**

- нормализация штрихкода: пробелы, кириллица, смешанная раскладка, пустая строка, только управляющие символы, строка длиннее лимита;
- схемы zod: номер макета с буквами, пробелами, `-1`, `1.5`, пустой строкой и ведущими нулями (`007` проходит и остаётся `007`); остаток отрицательный, дробный, `NaN`, больше `int32`; невалидная и граничная дата (29.02).

**API (`fastify.inject` + Testcontainers с реальным PostgreSQL):**

- CRUD позиций и контрагентов;
- дубли номера макета и штрихкода; разрешены после мягкого удаления старой позиции; `00123` и `123` — не дубль;
- восстановление позиции с занятым номером или штрихкодом возвращает 409;
- дубль контрагента с другим регистром и пробелами;
- конфликт `version`;
- списание больше остатка возвращает 422, и остаток не меняется;
- гонка: 20 параллельных списаний через `Promise.all`, итог строго равен сумме, ни одной записи журнала сверх успешных;
- инвентаризация во время параллельного списания;
- невалидный UUID, несуществующий ID;
- БД недоступна: 500 без стектрейса, `/api/health` отдаёт 503;
- CSV: BOM, разделитель, экранирование `;` и кавычек в названии контрагента.

**Фронт (Vitest + Testing Library):**

- хук сканера: быстрый и медленный ввод, короткий код, ввод в поле формы, снятие слушателя;
- формы: валидация, ошибки 409 и 422 с понятным текстом;
- состояния загрузки, пустое и ошибочное.

**e2e (Playwright):**

- «скан → найдено → списание → фокус вернулся в поиск»;
- «скан → не найдено → создание с заполненным штрихкодом»;
- удаление → отмена; удаление → восстановление из «Удалённых»;
- весь путь с клавиатуры без мыши;
- `@axe-core/playwright` на каждом экране.

## 11. Деплой на локальный сервер

- `deploy/docker-compose.yml`: сервисы `app` и `postgres:17`, том для данных PostgreSQL, `restart: unless-stopped`, healthcheck у обоих.
- Секреты (пароль БД) задаются в `.env`, который не попадает в репозиторий. В репозитории лежит `.env.example`.
- Миграции Drizzle применяются при старте приложения.
- Бэкап: `deploy/backup.sh` раз в сутки по cron делает `pg_dump -Fc` с ротацией 14 копий и кладёт копию на другой диск или сетевую папку. На этапе деплоя один раз вручную проверяется восстановление из бэкапа.
- Логи пишутся в stdout с ротацией Docker (`max-size`).
- Инструкция для пользователя на одну страницу: адрес в браузере, как сканировать, как списать, как восстановить удалённое.

## 12. Интеграция с 1С:Предприятие (этап 6)

Что закладывается уже сейчас: стабильные `id`, `external_id` у позиций и контрагентов, `updated_at`, мягкое удаление, журнал движений, OpenAPI-описание.

Платформа 8.3 умеет и ходить по HTTP (`HTTPСоединение`), и публиковать HTTP-сервисы, поэтому подходят все варианты ниже. Варианты по возрастанию сложности:

1. **1С забирает данные сама (рекомендую).** Регламентное задание в 1С по расписанию вызывает:
   - `GET /api/integration/labels?updatedSince=<ISO>` — изменённые и удалённые позиции;
   - `GET /api/integration/movements?since=<ISO>` — движения;
   - `GET /api/integration/counterparties?updatedSince=<ISO>`;
   - `PUT /api/integration/counterparties/:id/external-id` — 1С сообщает свой ID контрагента.

   Доступ по токену в заголовке `Authorization: Bearer`. В БД хранится только хеш токена.
2. **Приложение отправляет данные в HTTP-сервис 1С.** Нужна таблица `outbox` и фоновая отправка с повторами и экспоненциальной паузой, потому что 1С бывает недоступна, а данные терять нельзя.
3. **Обмен файлами** CSV или XML через общую папку, если конфигурацию 1С дорабатывать нельзя.

До начала этапа уточнить у того, кто сопровождает 1С:

- какая конфигурация (УТ, КА, ERP, Бухгалтерия, самописная) и можно ли её дорабатывать;
- как сопоставляются этикетки: номенклатура по штрихкоду, по номеру макета или отдельный справочник;
- как сопоставляются контрагенты: по ИНН (тогда в справочник добавляется поле `inn`) или вручную;
- в какую сторону идут данные: только из приложения в 1С или в обе.
